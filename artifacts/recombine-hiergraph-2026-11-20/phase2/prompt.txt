Generate a Canvas representation that onboards a senior developer to the
Ghostty core depicted in the supplied diagrams. Arrange the canvases in a

# Build the HierGraph

Inventory the core concepts across modular structure [M], dynamic calls [C],
ownership [O], and data dependencies [D]. Reconcile facts about the same
instance, operation or value. For each intersection, identify source branches
in at least two lenses and the source slice that supports their shared concept.
A shared name alone does not establish an intersection. Check the source.

Group those facts into CombinedDiagrams, each answering a concrete question.
Choose the organizing relation that suits the question. Retain each other lens
where it identifies an owner, explains a transition, or supplies an input.
Use actual functions, types, fields, or values alongside plain language that
explains what happens. At each transition name the concept the reader carries
forward. Keep pedagogical sequence separate from runtime calls.

Root -> canvas -> CombinedDiagram -> concept clusters -> source-backed leaves.
Each node has one parent; use a typed relation or jump for a fact that another
branch needs. Include pinned file ranges on evidence lines and name the input
tree branches that support the intersection. Account for the core depicted
across all four trees and identify any coverage gaps.

Target 3 canvases with 3-4 diagrams each. At the diagram-root frontier, lift
leaf relations to their two diagrams, drop self-loops and count distinct
directed diagram pairs once. Aim for an average of 6 intra-canvas pairs and
3 outgoing inter-canvas pairs per canvas. In the explanation also report raw
edge and jump counts for inspection. Miss a target if evidence warrants it.

<output format>
Return JSON matching output-schema.json: {explanation, rootCanvas, canvases, jumps}.

How the Hierarchical Graph maps onto this format:
- Each HierGraph canvas is one new canvas: {kind:"new",id,name,diagrams:[{id,ascii,position:{column,row}}],edges:[{source:{diagram,line},target:{diagram,line},label}]}. List canvases in reading order and set rootCanvas to the first one.
- Each diagram is one ASCII tree with exactly one root line. Indentation shows parenthood in P. Cite supporting source on the lines that carry it, as path:start-end.
- Intra-canvas edges go in that canvas's edges array. Each edge connects lines in two different diagrams of the same canvas. Start each label with the edge's lens type (depends, calls, owns or needs), then a short description, for example "calls: drains mailbox".
- Inter-canvas edges are jumps: {source:{canvas,diagram,line,startColumn,endColumn},target:{canvas,diagram,line}}. The source span covers the concept text on the source line; the target is the concept line it refers to. Jumps must connect different canvases, must not overlap on one line, and every canvas must be reachable from rootCanvas.
- Line numbers and columns are 1-based and inclusive: line 1 is a diagram's root line, and column 1 is the first character of a line. This applies to edge endpoints, jump sources and jump targets.
- Positions are nonnegative character-grid coordinates. Leave gaps based on actual text dimensions; do not overlap diagrams.

Keep explanation under 8,000 characters. In explanation, briefly cover: the intersections you found, each with its concept, lenses and kernel; candidates you rejected under I2; how you chose the structure and the alternatives you considered; the reading order; corrections made after checking the source; and the dimensions you produced next to the targets (diagrams per canvas, intra-canvas edges per canvas, inter-canvas edges per canvas, maximum depth), with reasons for any misses.

Use actual LF newlines in ASCII and printable ASCII characters in diagrams. Return no prose outside JSON. If validation-error.json exists, read it and previous-output.json and correct the output.
</output format>
