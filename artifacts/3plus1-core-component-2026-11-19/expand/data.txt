<task>
You are given a canvas of diagrams representing the core component of the codebase: the connected set of responsibilities around which the application's main behavior and state are organized.

Your task is to restructure this canvas in place. Choose which diagrams to expand; restructure each chosen diagram into a central diagram with a couple of peripheral diagrams connected to it. Return the complete canvas, including the diagrams you leave unchanged.

Framing

A tree diagram can relate components in two ways:

- Vertical (data dependency): depth means "is computed from". A child is an input its parent needs, and its own children are what that input needs in turn. Reading down a branch, you move from a result into what it is derived from.
- Horizontal (relational): values that inform one another without one being derived from the other at that point, e.g. a shared input used by several results, a value already expanded elsewhere and referenced by name, or an external input entering at several places.

A diagram is *flat* when its values sit side by side as top-level peers, even when one is actually computed from another, and the dependencies between them appear only as inline references. This hides what actually needs what.

Before:

  Podcast player
  |
  |-- Audio output: decoded samples to the device
  |-- Decoded samples: from the cached file
  |-- Cached file: downloaded episode bytes
  |-- Playback position: from seek target and elapsed samples
  |-- Listening progress: uploaded every 30s
  `-- Current episode: chosen from the queue

After:

  Podcast player
  |
  |-- Audio output
  |   `-- Compute: AudioEngine mixes decoded samples at the device rate
  |       |-- Decoded samples
  |       |   `-- Compute: decode(cached file, seek offset)
  |       |       |-- Cached file
  |       |       |   `-- Episode bytes from the feed URL [external]
  |       |       `-- Seek offset <- Playback position (reference)
  |       `-- Output device rate [external]
  |-- Playback position
  |   `-- Compute: seek target + elapsed samples / sample rate
  |       |-- User seek [external]
  |       `-- Elapsed samples, counted by AudioEngine
  `-- Listening progress
      `-- Compute: latest Playback position (reference) per Current episode
          `-- Current episode <- head of the user-ordered queue [external]

1. Choose which diagrams to expand
   - If the canvas holds a single diagram, expand it.
   - Otherwise, prefer to expand along the vertical dimension: choose diagrams with nodes that hide derivation of their own, i.e. inputs that are themselves computed from other inputs, and pull that structure out downward into new diagrams.
   - Avoid expanding sideways: do not add new peer topics that are only horizontally related to what the canvas already shows.
   - Leave a diagram unchanged when it is already small and focused; not every diagram needs expanding.

2. Restructure each chosen diagram into a central diagram
   - Give it a primarily *vertical*, data-dependency structure: nest each input under the value computed from it, so the shape of the tree alone shows what actually needs what.
   - Do not discard the horizontal relationships. Some components will not nest cleanly (e.g. a shared input used by many results, or a value already expanded elsewhere). Do not force these under a false parent or expand them twice; instead, express the relation as an annotated reference line at the specific computation that uses it.
   - The vertical structure is the skeleton; horizontal relations are laid over it.

3. Pull out concepts that should become their own diagrams
   - Each peripheral diagram should connect to the node in the central diagram, at the depth, that it elaborates.
   - Where a horizontal relation in the central diagram links two pulled-out concepts, connect those peripheral diagrams to each other as well.
   - A peripheral diagram goes deeper into its central diagram's scope; it does not widen that scope or repeat what another diagram on the canvas already covers.

4. Preserve the rest of the canvas
   - Keep the IDs of existing diagrams, including the ones you expand, so their existing edges stay attached. Return unchanged diagrams with their ASCII exactly as given.
   - Keep every existing edge. Re-point an edge only when restructuring moved or removed the line it pointed to.
   - Place new diagrams next to the diagram they expand. Existing diagrams may shift only to make room.
</task>
