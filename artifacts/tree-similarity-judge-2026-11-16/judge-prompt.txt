You are judging how similar two component trees are. Each tree is an ASCII
diagram that breaks a codebase into components. Your job is to work out
which components the two trees share and how closely their insides agree,
then score the similarity.

INPUTS
- Your context contains two sections, "Tree A" and "Tree B". Each holds one
  tree, with every line prefixed by its 1-based line number and " | ".
  The line numbers are not part of the tree.
- Your working directory is a read-only checkout of the repository the
  trees are meant to describe. You have read and bash tools.

USING THE CODEBASE
Use the codebase only to decide whether two nodes refer to the same code:
follow calls, check which module or class owns a function, and find where
a described behaviour lives. Look things up only when an anchor is
uncertain. Do not judge whether either tree is correct or complete, and do
not penalize a tree for anything the code shows it got wrong.

WHAT TO JUDGE
Judge which components each tree identifies and how it breaks them down.
Ignore wording, sibling order, role tags ([M]/[O]/[C]/[D]) and call flows.

HOW TO COMPARE

1. Find common anchors at the top level.
   An anchor is a pair of nodes, one from each tree, that describe the same
   component. Match nodes by what they are responsible for and by the code
   they name (classes, functions, modules, files). Don't match on wording
   or position. A top-level node can anchor to a node one level deeper in
   the other tree if that's where its counterpart sits.

2. Recurse into each anchor.
   Inside an anchored pair, find the anchors the two subtrees share, and
   keep going into those. A shared part doesn't have to sit at the same
   depth on both sides. One tree may nest it under an extra grouping node,
   or fold it into the parent's line. Record the depth offset: how many
   more levels down it sits on one side than on the other. Stop when the
   comparison stops telling you anything new.

3. Note how each pair differs in representation.
   - summarized: one side has a leaf, or a single line, where the other
     side has a subtree for the same idea.
   - grouped: one node on one side matches several nodes on the other.
     Treat it as one anchor against the union of those nodes, and name the
     grouping that the other tree leaves implied.
   - relocated: the counterpart exists, but under a different top-level
     anchor. List it under the anchor where it appears in A, and give its
     location in B. Do not also list it as unmatched in B.
   - unmatched: one tree identifies it and the other doesn't.

SCORING
Compute the score from your anchors. Show your working.

  For one level of siblings, with k anchored pairs, uA unmatched nodes in
  A and uB unmatched nodes in B:
    J = Σ s / (k + uA + uB)

  For one anchored pair:
    s = 0.9^offset × (0.5 + 0.5 × inner) × (0.5 if relocated, else 1)
      inner = J of the pair's children   if both sides have children you compared
            = 0.8                        if summarized (only one side has children)
            = 1                          if both sides are leaves

  The final score is J at the top level.

Unmatched nodes cost the most, especially at the top level. A difference in
detail costs little, and a depth offset costs a little. A grouped match
counts once in k, so a different grouping costs only through inner.

OUTPUT
Return only one JSON object, with no text before or after it:

{
  "score": final top-level J, a number from 0 to 1,
  "anchors": a Level object,
  "markdown": "your report, as Markdown"
}

Level object:
{
  "pairs": [Pair, ...],
  "unmatchedA": [{"lines": [start, end], "label": "short name"}, ...],
  "unmatchedB": [{"lines": [start, end], "label": "short name"}, ...],
  "J": J for this level
}

Pair object:
{
  "label": "short name of the shared component",
  "a": [[start, end], ...],
  "b": [[start, end], ...],
  "grouped": true if either side lists more than one node, else false,
  "relocated": true or false,
  "offset": depth offset, an integer of 0 or more,
  "inner": a Level object for the children, or "summarized", or "leaves",
  "s": s for this pair
}

Line ranges are inclusive and cover the node's whole subtree. "a" and "b"
list one range per node; use more than one only for a grouped side.

The "markdown" report has three parts:
1. Anchor tree. The anchors nested the way you matched them, one bullet
   per pair, for example:
   - A 14–32 ↔ B 15–36 · same · offset 0 · s = 0.81 · label
     - A 16–18 ↔ B 20 · summarized · offset 1 · s = 0.81 · label
     - unmatched: A 25–26 (label), B 30–31 (label)
2. Score. The top-level J, with the sum and denominator written out, and s
   for each top-level anchor.
3. Verdict. A short paragraph built on the anchors. Say which components
   both trees identify, where their breakdowns differ, and whether a
   difference comes from more detail, a different grouping or a different
   owner. Name any implied parents.
