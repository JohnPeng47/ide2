## Rubric: compare level by level

- Match by shared names (classes and functions), not by wording.
- File paths count as weak evidence, because `agent-session.ts` shows up everywhere.
- Score each cluster 3/3, 2/3 or 1/3.

**L2 – Placement.** For each concept that appears in two or more runs, check whether it sits under the same cluster. If not, label it **relocated**, not missing. Also name the run's organizing approach (grouped by owning class vs. grouped by flow), because that usually explains most relocations.

**L5 – Singletons.** Details that appear in only one run. Classify each as valid extra depth, an error, or noise. Don't penalize differences in depth below level 2 or 3; you're measuring whether the same components are found, not how detailed the descriptions are.

It's the metric I used for "anchor agreement" (the 95–100% figure). It's loose in a few specific ways. Here's how it works in `analyze.py:28-36`:

1. Take each judgement's **top-level** anchors only, as (A range, B range) pairs.
2. Two anchors from different judgements count as "the same" if their A ranges overlap **by at least one line** and their B ranges also overlap by at least one line.
3. Agreement = 2 × matches / (anchors in judgement 1 + anchors in judgement 2).

That leaves three blind spots:

- **Partial overlap counts as full agreement.** Say one judge anchors `A 40–60 ↔ B 53–69` and another anchors `A 40–60 ↔ B 54–59`. They share 6 of 17 B lines and still count as identical. This is exactly what happened in Astra's 0.739 outlier on Mapping v2↔v4·2: it anchored only part of B's branch and left the rest unmatched. The metric scored that as agreeing with the other runs, so the 0.95 hides the disagreement that caused the score drop.
- **Only the top level is compared.** Two judges can split the top level identically and then match completely different children underneath, and agreement is still 1.0.
- **Labels are ignored.** Grouped, relocated and offset aren't checked. In Sol's 0.757 run, it marked session/history as *relocated* while the others marked it *grouped*. That's the main source of the score difference, and the metric never looks at it.

So "1.0 on Ghostty" means "the judges carved the top level into roughly the same chunks". It doesn't mean "they agreed on the anchor tree".

A stricter version could:
- weight each match by how much the line ranges overlap (intersection over union), instead of any overlap counting;
- recurse into `inner`, so children are compared too;
- count agreement on grouped/relocated/summarized for each matched pair.

1. **A level** (a set of siblings): `J = Σ pair scores / (pairs + unmatched on either side)`

   - If both sides are leaves, inner = 1. If only one side has children ("summarized"), inner = 0.8.
   - *offset* is how many levels deeper the node sits on one side than the other.

## Why it happens

Mostly it's the prompt. It says "Keep each range tight", "stop when the source establishes it", and "a parent does not need the union of every descendant's mappings". The agent follows that literally: it maps the few lines that *prove* a claim, not the full extent of what the node *is*. The validator only checks bounds and node references, and the coverage metric counts "node has ≥1 range". So nothing pushes back on a 3-line mapping for a 19k-line component.

## How I'd improve it

1. **Define two kinds of range.** Give each node an *extent* (the full function, struct or file region it names) and keep the tight *evidence* ranges alongside. The current prompt asks only for evidence, but source navigation needs the extent.
2. **Resolve symbols deterministically instead of asking the model for line numbers.** `sourceRange` already has a `symbol` field. 3. **Make `validate_source_mappings` report gaps, not just bounds.** Flag functions or `file:line` references named in a label but not covered, ranges that start mid-function or contain only a signature or doc comment, and container nodes mapped to fewer than N lines. The agent already reruns the validator when it reports errors, so it would fix these too.
4. **Make missing coverage explicit in the output.** Change the schema to `{node, claims: [{claim, ranges | unsupported}]}`. Extracting claims first and then finding evidence per claim gives you a measurable claim-coverage number and replaces the empty `notes`.
5. **Set a rule for container and summary nodes.** `[M]`/`[O]` headers and root nodes should map to the declaring struct or file, or reference their children's extents. On canvases, overview nodes should reuse the mappings of the detail diagram that expands them.
6. **Replace the headline metric.** Report named-symbol coverage (the last table column, which is cheap and deterministic), claim coverage, and a judge pass on whether a reader could verify the node from its lines. Coverage weighted by range length would also expose the 3-line problem.
7. **If it's still thin, split the work.** One pass per subtree, or per detail diagram on canvases, gives each node more reading budget than a single pass over 150 nodes.
