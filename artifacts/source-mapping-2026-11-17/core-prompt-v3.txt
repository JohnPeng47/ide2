Map the provided diagram’s nodes to the source-code line ranges that explain or implement them.

For each node, select the source ranges that together explain what the node represents. Read the label in the context of its branch. A single-line leaf can stand for an entire subsystem. Use the following rules to decide when you have enough evidence.

- For a specific fact, stop when the source establishes it. A declaration listing all allowed states can fully support a node that simply names those states.
- For a subsystem, identify its principal responsibilities in the pinned source and follow its entry point to where those responsibilities are implemented. For a compound label, check each named behavior, resource, or ownership claim. A field declaration can establish who holds a resource. If the label also describes its lifetime, find where the owner acquires, transfers, or releases it, as applicable.
- For a flow, follow the handoffs in the label. Select the code that connects the steps and performs the named transformations. A caller that delegates the work may be a useful first jump. Follow the call to the implementation when the label describes what that work does.

Keep each range tight. Use several disjoint ranges in one file or across files when the evidence is distributed. Choose ranges for the node itself, using its parent and children to clarify scope. A parent does not need the union of every descendant’s mappings, and a child may need direct evidence beyond its parent’s range.

Before validating, review each node against its selected lines. Could a reader verify each material claim from those lines? Follow any missing claim into the source. If only part is supported, keep the verified ranges and identify the diagram, node, and unresolved claim in notes. If no part is supported, leave the node unmapped and explain why in notes. Carry every verified range into the complete candidate and final submission.
