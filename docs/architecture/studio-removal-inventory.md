Important retained boundaries:

- Keep `src/features/mapping/`, `application/mapping/`, `domain/mapping/`, `infrastructure/mapping/` except the selective dependency/navigation cleanup above.
- Keep Mapping diagram content, parser/interpreter, grid, camera, selection, source context, jumps, connections, saved projections and compaction projection primitives. Similar Studio names do not imply those Mapping implementations are removable.
- Keep `application/core/source/projectSource.ts`, core corpus/language-service infrastructure, `domain/core/source/sourceNavigation.ts`, and Mapping source-context migration.
- Keep `src/shared/diagrams/DiagramText.tsx`, its CSS/test, and Mapping change-session diff code. These are distinct from Studio's old DiagramView/partialDiff chain.
- Keep Mapping browser/performance tests, their support fixtures, and `packages/ui-test-framework/`.

The key cleanup dependency is `resolveDiagramSource`: at present it reads DiagramSet source bindings even for Mapping. Saved representations already carry their own source bindings, but removing the fallback must account for sources registered only through Studio sets. The second dependency is `FileCompactionService` accepting the broad `CoreApplication`, although it only uses store/corpus capabilities.

Persisted-data scope is separate from this source-code inventory. `.diagrams/`, `.diagrams-code/`, `.diagrams-parent-architecture/`, configured `.datasets` directories, and `.materialized-parent-manifests/` are not blanket deletion targets: they contain saved data, examples, provenance, and/or fixtures. Existing projection tests read `.diagrams-parent-architecture/representations/catalog.json`. Catalog revisions remain useful in Mapping even when originally promoted from Studio. Similarly, parser research under `tools/diagram-parser/`, `projection-3d/`, vendored `softwarez/`, and `.skills/map-diagram-sources/` are not classified as Studio/Experiment code merely because they concern diagrams or research.

Evidence: enumerated repository paths; traced relative import consumers across application/domain/infrastructure/frontend/server/tools/tests; inspected shared facade, routes, source resolver, persistence and startup code; checked string-based browser/API integrations. This is a static dependency inventory, not a deletion-build validation. Deleting all `yes` entries still requires coordinated edits to the `maybe` entries, removal of obsolete imports/type exports, fixture updates, and then typecheck/build/Mapping tests.
