READING THE MEASUREMENTS

Sizes below use decimal KB (1 KB = 1,000 bytes).
R = complete response value serialized in recorded command stdout.
P = projection, preview, or excerpt printed by the agent's script.
W = complete MCP wrapper printed in stdout, including duplicated representations.
? = not recorded; the historical temporary file is no longer present.

These are UTF-8 text sizes, NOT measured network traffic or token counts.
Python and JavaScript serialization differ: the exact same first search page
is 35,211 bytes in B's Python output and 33,807 bytes in A's compact JS output.
Command stdout comes from event_msg/item_completed/CommandExecution records,
which retain more output than the truncated tool result shown to the model.
Full stdout sizes must not be interpreted as exact model-context sizes.

Times are recorded whole-command durations, including process startup, MCP
initialization, serialization, and local processing. No individual HTTP-call
latencies were recorded inside these commands. Each batch duration is counted
once; its children share that timing and must not be assigned the batch time
individually. Concurrent branches overlap.

FINDINGS AND DESIGN IMPLICATIONS

1. Duplicate discovery representation is proven, not estimated.
   A's complete printed MCP result is 49,737 bytes for 23,251 bytes of logical
   docs (2.14x). json.loads(content[0].text) == structuredContent.result.
   B's 51,628-byte form adds Python whitespace and the JSON-RPC envelope.
   The client could project one representation; do not assume every MCP host
   injects both into model context. Here the discovery script printed both.
   Current infrastructure/mapping/mcp/server.ts also emits both fields.

2. Empty search acts as a line dump instead of a discovery index.
   100 hits serialize to 33,807 compact bytes; snippet strings total 5,767
   bytes. The rest is identifiers, metadata, field names, and JSON structure.
   Five common identity fields need not be repeated on every result:
   origin, representationId, revisionId, name, nodeId.
   Grouping these fields once preserves every hit
   and reduces this page to 8,578 bytes: 74.6% smaller, verified losslessly.
   See grouped-search-example.json for that exact alternative.

3. Read access through exec caused fallback work.
   Both sessions receive HTTP_WRITES_DISABLED for canvas.list(). B first
   misses requestId, then tries two server ports. A successfully uses the
   direct GET listing and live short-context endpoint instead.
   A dedicated read-only catalog/list tool would avoid read intent passing
   through a mutation-oriented exec gate and version/requestId conventions.
   These are observed historical failures, not an assertion about every
   current server configuration.

4. "Short context" still requires client-side selection.
   A fetches nine complete short contexts before selecting relevant diagrams.
   Its local index of all 38 diagram titles/IDs/line counts is only 4.865 KB.
   B constructs an even smaller 2.467 KB inventory by reading 1,550 line hits.
   Offer that inventory directly, including saved documents when no live
   canvas is attached. Then offer selected diagram ASCII/source refs/edges.
   Full historical short-context bytes are unavailable: this audit cannot
   quantify their overhead or honestly claim a total network-byte saving.

5. Discovery should start small.
   Empty canvas-api-search returns schemas/examples for 18 methods; A then
   separately requests canvas.attach and nodes.list documentation anyway.
   A compact method index plus targeted documentation would reduce initial
   context consumption. Existing AGENTS.md specifically directs empty-query
   discovery, so this cost is encouraged by the documented workflow.

6. Timing points to workflow cost; it does not isolate backend latency.
   A's docs/search batch is 24.222s, live-context batch 13.855s (overlapping).
   B's 16-page enumeration is 23.492s, full eight-document reads 9.675s.
   Historical records do not attribute those seconds to individual calls,
   browser polling, saved-data loading, or startup. Add per-call telemetry
   before choosing which backend operation to optimize.

Suggested read workflow (proposal; these tool names are not implemented):

answer a diagram question
|-- catalog(scope=live+saved, fields=ids,titles,versions,lineCounts)
|-- search(query, groupBy=diagram, maxHitsPerDiagram=3, maxBytes=...)
`-- read(diagramIds, fields=ascii,sourceRefs,edges, optionalLineRanges)
    `-- Return one selected representation to the model

Record requestId, method, parameters excluding sensitive data, elapsedMs,
HTTP-body bytes, MCP-result bytes, model-visible bytes, hitCount, nextOffset,
and truncation status separately. That distinguishes expensive retrieval
from inefficient presentation.
